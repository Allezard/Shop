# Shop.Reference — карта этапов

Эталонная реализация `Shop.Workspace`. Здесь лежит **конечное** состояние — то, что
получается после всех модулей.

> [!warning] Подглядывайте после попытки, а не вместо неё
> Решения заданий продублированы во врезках самих модулей — чаще нужно
> посмотреть один метод, а не открывать проект целиком.

---

## Как читать, находясь в середине курса

В конечном состоянии перемешано то, что появлялось в разных модулях. Чтобы
было видно, что относится к вашему текущему месту, каждая строка помечена
номером модуля:

```csharp
public string? PhoneNumber { get; set; }                    // ← 06
```

```csharp
b.HasIndex(o => new { o.CustomerId, o.PlacedAt });          // ← 05
```

Пометка `// ← 05` значит: **эта строка появилась в модуле 05**. Если вы
проходите модуль 02, её у вас быть не должно, и её отсутствие — не ошибка.

Пометка в начале файла (`namespace Shop.Domain;   // ← 02`) относится ко
всему файлу: он целиком создаётся в этом модуле.

## Что появляется в каком модуле

### Модуль 02 — модель

| Файл | Что в нём |
|---|---|
| `Domain/Address.cs` | комплексный тип, а не owned: значение без идентичности |
| `Domain/Customer.cs` | ключ UUID v7, уникальный email |
| `Domain/Order.cs` | корень агрегата, строки в составе |
| `Domain/OrderLine.cs` | часть агрегата заказа |
| `Domain/Product.cs` | ключ `bigint`: товары заводим только мы |
| `Domain/Category.cs`, `Tag.cs` | справочники, связь многие-ко-многим |
| `Domain/Payment.cs` | иерархия из трёх типов, TPH |
| `Domain/Review.cs` | ключ v7 — понадобится в модуле 05 |
| `Data/ShopContext.cs` | свойства `DbSet` и `ApplyConfigurationsFromAssembly` |
| `Data/Configurations/*.cs` | по файлу на сущность |

Ключевые решения: v7 вместо v4 для всего, что часто вставляется;
`Restrict` между агрегатами и `Cascade` внутри; TPH с проверочными
ограничениями взамен потерянного `NOT NULL`.

### Модуль 03 — запросы

| Файл | Что в нём |
|---|---|
| `Queries/OrderQueries.cs` | проекции вместо `Include`; детали заказа без декартова произведения |
| `Queries/ProductQueries.cs` | `ILike` вместо `ToLower().Contains()`; каталог без `AsSplitQuery` |

Смотреть стоит на то, чего **нет**: ни одного `Include` на пути чтения,
ни одного `AsSplitQuery`, ни одного `ToList()` перед `Select`.

### Модуль 04 — отслеживание и границы

| Где | Что |
|---|---|
| `Program.cs` | `UseQueryTrackingBehavior(NoTracking)` по умолчанию |
| `Domain/Order.cs` | нет навигации на `Payment` — это отдельный агрегат |
| `Configurations/OrderConfiguration.cs` | маркер конкурентности через системную колонку `xmin` |
| `Services/ReservationService.cs` | атомарный резерв одной командой |
| `Services/ImportService.cs` | пакеты по 200 с очисткой трекера |

Отдельно стоит прочитать комментарий в `ReservationService`: маркер
конкурентности для остатка склада был бы **неверным** ответом.

### Модуль 05 — индексы

| Где | Что |
|---|---|
| `OrderConfiguration.cs` | составной `(CustomerId, PlacedAt)`; частичный по редкому статусу |
| `ProductConfiguration.cs` | частичный покрывающий; триграммный `gin_trgm_ops` |
| `ReviewConfiguration.cs` | **отсутствие** индекса по дате — и объяснение почему |
| `Queries/ReviewQueries.cs` | keyset-пагинация по первичному ключу |

`ReviewConfiguration` — самый поучительный файл: у самой пишущей таблицы
ровно два индекса, и это прямое следствие выбора ключа в модуле 02.

### Модуль 06 — миграции

| Где | Что |
|---|---|
| `Domain/Customer.cs` | `PhoneNumber` — результат переименования четырьмя выкладками |
| `Migrations/…AddSearchInfrastructure.cs` | `CONCURRENTLY`, `NOT VALID`, `lock_timeout` |

Автоматически сгенерированных миграций здесь нет: они воссоздаются командой
`dotnet ef migrations add` и в эталоне только занимали бы место. Есть
образец **рукописной** — с тем, что модель EF не выражает.

### Модуль 07 — транзакции

| Где | Что |
|---|---|
| `Domain/OutboxMessage.cs` | исходящие сообщения |
| `Services/CheckoutService.cs` | три фазы, внешний вызов вне транзакции |
| `Services/OutboxPublisher.cs` | публикация, метрика отставания, чистка архива |
| `Program.cs` | `EnableRetryOnFailure` |

`CheckoutService` — самый насыщенный файл эталона. Обратите внимание на
`RecoverStuckAsync`: исходное требование «не должно остаться заказа без
платежа» выполняется **им**, а не транзакцией.

### Модуль 08 — тесты

Проект `demo/Shop.Tests`: три уровня проверок и база в контейнере.

## Запуск эталона

База у него своя, чтобы не мешать вашему `Shop.Workspace`. Имя базы образуется от имени проекта: точка меняется на подчёркивание, регистр — нижний.

```powershell
cd demo/Shop.Reference
dotnet ef database update
dotnet run                       # порт 5082
```

```bash
cd demo/Shop.Reference
dotnet ef database update
dotnet run                       # порт 5082
```

| Проект | Порт | База |
|---|---|---|
| `Shop.Legacy` | 5080 | `shop_legacy` |
| `Shop.Workspace` | 5081 | `shop_workspace` |
| `Shop.Reference` | 5082 | `shop_reference` |

Все три можно держать поднятыми одновременно и сравнивать планы запросов
на одинаковых данных.

## Чего в эталоне нет намеренно

| | Почему |
|---|---|
| Контроллеры | не про EF Core; добавляются тривиально |
| Сгенерированные миграции | воссоздаются командой |
| Реальная шина сообщений | `IMessageBus` — интерфейс, реализацию подставляйте свою |
| Наполнение данными | адаптируйте `demo/tools/seed.sql` под свою схему |
